# 建图定位与固定路线接口契约

执行基线v2.1，2026-11-11。M2/M4/M5据此接线；架构与两种模式详见[方案](建图定位与固定路线方案.md)，启动进度见[运行说明](运行说明.md)。保留六类标准板端/模块接口；定位组件的标准内部话题和TF另外列出，无自定义消息。

## ROS接口与唯一发布者

| 话题 | 类型 | 发布者→消费者 | 约定 |
|---|---|---|---|
| /cmd_vel | geometry_msgs/msg/Twist | M4执行器→M2 | +x车头、+z逆时针、linear.y=0；建议20Hz；自动模式唯一发布者；断流0.5s内固件停车 |
| /odom | nav_msgs/msg/Odometry | M2→EKF | 原始轮式反馈；frame_id=odom、child_frame_id=base_footprint，m/rad，时间戳新鲜；仅M2发布 |
| /imu/data | sensor_msgs/msg/Imu | M2→EKF | angular_velocity.z为rad/s，frame_id=imu_link；安装朝向/偏置实测，当前融合主要用角速度z |
| /lifter | std_msgs/msg/UInt8 | M5→M2 | 0降/1升，其他值拒绝；重复同值不冲击；实测等待，不构造虚假到位反馈 |
| /scan | sensor_msgs/msg/LaserScan | 雷达→SLAM或AMCL、M4保护 | 必需；frame_id=laser，rad/m，外参实测；断流不能继续记为定位正常 |
| /qr | std_msgs/msg/String | M3→证据记录 | 保留扫码能力，固定路线不以QR推进；核对本组正式随机串 |

| 定位内部输出 | 唯一发布者/用途 |
|---|---|
| /odometry/filtered | EKF输出，M4固定路段使用的连续局部反馈 |
| TF odom→base_footprint | 只由EKF发布，固件关掉同一TF广播 |
| /map、TF map→odom（建图） | slam_toolbox；建图模式，mission关闭 |
| /map、/amcl_pose、TF map→odom（执行） | map_server发地图，AMCL发位姿/全局TF；执行模式不运行SLAM |
| 车体/传感器静态TF | robot_state_publisher，M1/M4实测外参 |

**待实现接线**：EKF的odom0设为/odom；输出保留/odometry/filtered，删除旧launch将输出映射回/odom的做法。不relay /odom→odom/unfiltered，不让原始与滤波结果争用话题。不直接照用旧navigation/slam launch而忽略接线差异。

执行模式可用Nav2的定位组件map_server+AMCL，不启动planner/controller/旧waypoint_driver。建图遥控、自动执行和手动兜底互斥；任何时刻/cmd_vel只有当前模式的一个发布者。急停由物理开关实现。

原始odom建议≥20Hz、IMU建议≥50Hz；记录实际频率及最大间隔。局部反馈数据年龄初始建议0.3s，scan/TF超时按实测冻结，不能将该建议不加验证地用于所有输入。首次地图定位初始化后才能开始联合运行。定位健康检查结合scan新鲜度、TF可用性、节点状态与实际运动响应；不要求固定AMCL发布频率或厘米级协方差阈值。定位链路失效则停车，普通波动记日志；各输入micro-ROS时间同步由M2验证。

## 板端当前实现（2026-11-19）

`/cmd_vel`、原始 `/odom` 和 `/imu/data` 已在正常固件实现并烧录；`/lifter` 已改为180°位置控制，默认0°/80°、免arm，新版已见板端诊断（当前0°/75°），实物端点/载荷待标定，不能把软件完成视作板端已验收。本次补偿后静态odom20.001Hz、IMU47.985Hz，IMU 为 best effort；姿态不可用（orientation_covariance[0]=-1），角速度/加速度协方差未知，陀螺XYZ已扣除静态零偏并复测，加速度仍保留重力；[校准记录](../../tests/firmware/2026-11-19_imu_calibration.md)已归档。安装外参、重启/温度重复性、约48Hz节拍及EKF消费仍需验证，详见[M2进度与交付清单](M2底盘进度与交付清单.md)。

当前源码已按用户要求移除无反馈/反向反馈四轮停车锁存（用户确认移除后基本移动和简单定时命令组有效）。诊断用 `feedback_guard_enabled=false` 标识，旧mask字段已移除；编码器仍参与PID/odom，480ms命令超时、显式零速和升降互锁保留。

用户纠正轮ID接线后，四轮向前滚动时原始编码器count均增加。固件参考 `4943022` 撤销四轮取反，PID/odom直接使用原始增量；诊断counts增量和speed/target前进均为正。用户确认恢复后基本移动和简单定时运动初步有效；量化精度与物理停车仍待实测。

额外 `/chassis/diagnostics` 为开发期只读 JSON（std_msgs/msg/String、best effort、约2Hz），不用于任务状态推进。IMU 读取失败或样本陈旧会停止 IMU 发布，不自动禁止电机命令；M4/M5 仍负责必要反馈失效停车。板端通信异常后停车等待 RESET，尚无自动断线恢复。物理停车时间、急停与重启行为未完成验收。

## 升降接线与控制（新增源码，尚未上板验收）

用户已纠正S1/GPIO8的MG996R实际为180°位置舵机。`/lifter=1/0`直接选择上/下目标角度，menuconfig默认80°/0°；无需arm，首次命令前不发PWM，等待结束持续保持目标脉宽。相同目标幂等，等待中反向拒绝。无外部到位反馈，`lifter_position_confirmed=false`。

仅保留 `/lifter/stop`（Trigger）撤销PWM，无法无反馈保持中间位置；旧arm/jog服务已移除。人工stop后新0/1直接恢复，硬故障排查后RESET。0是下降，不是停止。M5发送升降前底盘零速并停稳，按实测稳定时间加余量等待，故障不推进。默认端点脉宽需脱载验证，详见[升降控制](../../firmware/chassis/LIFTER.md)。

## M4执行器与M5状态机

采用一个mission进程导入M4的Python执行组件，无新增action/topic与双速度发布者。以下是**待实现Python约定**：

```python
executor.start(segment)         # 校验后开始，同时仅一个动作
status = executor.tick()        # 非阻塞：RUNNING / SUCCEEDED / FAILED
executor.stop(reason)           # 立即零速并取消；重复调用安全
```

动作为drive/turn/wait；drive.distance_m有符号，turn.angle_rad有符号，wait.duration_s为等待时间；每段有id、有限timeout_s、速度与误差限值。M4管理局部反馈/控制、定位健康、近障检查、到位及故障零速，M5管理顺序、升降、计时和失败锁存。截止/取消优先于SUCCEEDED；停止检查不能被等待阻塞。

例（设计，未实现）：M5提交`{id: A_enter, kind: drive, distance_m: 0.10, timeout_s: <实测值>}`；M4用/odometry/filtered增量闭环，到位停稳后返回SUCCEEDED；M5才发/lifter=1。AMCL此时真实定位与记录，但其跳变不直接成为0.10m动作的增量。反馈失效或超时返回FAILED并零速，不推进举升。

## 测量与交接

M3填[标定表](固定路线标定表.md)，M1签认机械容差，M4生成唯一执行配置与场地/地图/任务局部坐标关系，M5绑定版本验收。出生时用当前局部位姿建立任务变换，不重置EKF里程计；AMCL按已保存地图中的真实出生位姿初始化。旧dock_points.yaml是图纸初值，不能直接当实测位姿。

## 接口观察

先按[运行说明](运行说明.md)source环境、启动固件/agent及改造后的定位模式。`ros2 topic echo /odom --once`看原始反馈，`ros2 topic echo /odometry/filtered --once`看滤波输出，`ros2 run tf2_ros tf2_echo map base_footprint`看全局位置；`ros2 topic info /cmd_vel -v`查速度发布者。后两个定位观察须真实链路已启动；新启动方式与执行器仍待实现，不把观察命令当作已通过证据。
