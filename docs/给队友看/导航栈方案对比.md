# 技术选型：linorobot2 全栈 vs Yahboom 方案

> 起因：linorobot2 自带 **ROS 2 + Nav2 + Gazebo + slam_toolbox + EKF** 完整链条。
> 问题：能否直接采用，从而**同时减轻 M2 与 M4 的压力**？两边如何横向比较？
> 核实日期：2026-10-22（两个仓库均实际 clone 并逐文件核对）。

---

## 1. 直接回答

**可以，但不能"整包照搬"，要拆开看：**

- **对 M4：明确大幅减负** ✅（这是最大收益）
- **对 M2：只算部分减负，而且会引入新的适配风险** ⚠️
- **最优解是"混合"**：**M2 保留 Yahboom 板载固件，M4 采用 linorobot2 导航栈**。

理由见下。核心矛盾是：**linorobot2 的固件（Arduino）与 Yahboom 的板子（ESP-IDF + 板载驱动 + 板载 IMU）不是一套**，而**两侧之间只是标准 ROS 话题**——所以最优是各取所长。

---

## 2. 为什么 M4 能大幅减负（逐条对应 M4 任务）

linorobot2 的 `jazzy` 分支实际包含 6 个包：

| 包 | 内容 | 对应 M4 任务 |
|---|---|---|
| `linorobot2_description` | URDF/xacro，**含 `mecanum.urdf.xacro`** | M4-6 footprint |
| `linorobot2_base` | `config/ekf.yaml`（robot_localization） | M4-3 定位 |
| `linorobot2_navigation` | `slam.launch.py`(slam_toolbox)、`navigation.launch.py`(Nav2)、`config/{slam,navigation}.yaml`、`maps/` | **M4-2 / M4-4 / M4-5 / M4-8** |
| `linorobot2_bringup` | 统一 bringup、sensors、joy_teleop | M4 集成 |
| `linorobot2_gazebo` | **Gazebo 仿真**（worlds/models/launch） | 离线验证（免硬件） |
| `linorobot2` | 元包 | — |

核实到的细节：

- `navigation.launch.py` 直接 `IncludeLaunchDescription` 调 **`nav2_bringup/bringup_launch.py`** 并传入自带 `navigation.yaml` → **AMCL + map_server + costmap + planner/controller 全是现成的**。
- `amcl` 使用 **`DifferentialMotionModel`**；控制器是 `RotationShimController` + `RegulatedPurePursuitController`。
- `slam.launch.py` 调 **`slam_toolbox/online_async_launch.py`** + 自带 `slam.yaml`。
- `ekf.yaml`：`two_d_mode: true`，融合 `odom/unfiltered` + `imu/data`，`publish_tf: true`。
- 许可证 **Apache-2.0**（保留署名即可用于课程项目）。

**结论**：M4 从"从零搭导航"变成"**改参数 + 标定停靠点**"。M4-1/2/3/4/5/8 基本白送，只剩 M4-7（停靠点）和 M4-9（冻结）要自己干。

> 重要发现：**linorobot2 的 Nav2 也是差速控制器**（RPP + AMCL DifferentialMotionModel），**并不使用麦轮横移**。这印证了我们《底盘参考实现》§8 的判断——**"先不开横移"是行业通行做法，不是我们的妥协**。

## 3. 为什么对 M2 不是"白送"（三个硬缺口）

`linorobot2_hardware` 的固件库很全：`encoder / motor / pid / kinematics / odometry / imu / battery / lidar / wifi`。
**但它是 Arduino + PlatformIO 写的，配置里没有 Yahboom 板。**

| 缺口 | linorobot2 提供的 | Yahboom 板实际是 | 代价 |
|---|---|---|---|
| **电机驱动** | 仅支持 通用2路方向(INA/INB)/通用1路/**BTS7960**/ESC | 板载集成驱动（电机直接插 `M1+/M1-`） | 需要拿到板载驱动的 PWM/DIR 引脚映射才能套用，否则要自己写电机层 |
| **IMU** | GY85 / BNO085 / MPU6050 / MPU9150 / MPU9250 / **QMI8658** | **ICM42670P**（板载、I2C） | **不在列表里**，要自己加驱动，否则放弃 EKF |
| **工具链** | Arduino / PlatformIO | **ESP-IDF**（官方例程同款） | 二选一，不能混用 |

另外两点要注意：
- linorobot2 的 `odometry.cpp` 文档明确写的是**差速方程**（虽然 `kinematics.h` 有 `MECANUM` 逆解）。
- 固件发布 `odom/unfiltered`，frame 用 `odom` / `base_footprint`；**Yahboom 例程用的是 `odom_frame` / `base_footprint`** → frame 名不一致，需要统一。

**结论**：M2 若整包改用 linorobot2 固件，**要先做两个移植（板载驱动 + ICM42670P）**，这和"减轻 M2 压力"的初衷相反。

## 4. 三种架构方案对比

| 维度 | **A. 全 Yahboom** | **B. 全 linorobot2** | **C. 混合（推荐）** |
|---|---|---|---|
| M2 固件 | ESP-IDF 官方例程（**板载驱动/IMU 原生支持**） | Arduino 移植（**要移植驱动 + IMU**） | ESP-IDF 官方例程 |
| M4 导航 | 自己搭 Nav2/SLAM | linorobot2 全套 | linorobot2 全套 |
| M2 工作量 | 低 | **中高（移植风险）** | 低 |
| M4 工作量 | 高 | **低** | **低** |
| 麦轮运动学 | 差速（无横移） | 有 `MECANUM` 但 Nav2 不用 | 差速（无横移） |
| 仿真 | 无 | **Gazebo 现成** | **Gazebo 现成** |
| 风险 | M4 全靠自己 | **板子适配失败 = 卡死** | 中等（只需对齐话题/frame） |
| 契合需求 PDF | 高（同板同电机） | 中 | **高** |

**选 C。** 它把两个风险都规避了：M2 用最稳的板载固件，M4 用最全的开源栈，中间用标准话题对接。

## 5. 方案 C 的接口影响（需要谈判）

采用 linorobot2 的 EKF 后，我们的"5 话题契约"要变成 **6 个**：

| 变化 | 原 | 现 | 说明 |
|---|---|---|---|
| 里程计 | `/odom` | `odom/unfiltered`（或 remap 保持 `/odom`） | 建议 **remap**，不改 M2 固件 |
| **新增** | — | **`/imu/data`** | **EKF 需要 IMU 偏航角速度；板载 ICM42670P 已具备** |
| frame | — | `odom` / `base_footprint` | 把 Yahboom 的 `odom_frame` 改名 |
| 其余 | `/cmd_vel`、`/scan`、`/qr`、`/lifter` | 不变 | — |

> ⚠️ 这打破了之前"只有 5 个话题"的约定。**多出的 1 个话题换来了明显更稳的定位**（IMU 直接测角速度，弥补麦轮打滑导致的里程计 yaw 漂移）——我认为值得，但需要你拍板。

## 6. 与 YahboomTechnology/MicroROS-Board 的横向比较

| 维度 | Yahboom MicroROS-Board | linorobot2 | 我们怎么用 |
|---|---|---|---|
| 定位 | **板子官方资料**（教程 + 硬件说明） | **开源工程**（可 clone、可改） | 都要 |
| 与本套硬件的匹配 | **100%**（同板同电机同 IMU） | 0（需适配） | M2 用 Yahboom |
| 底盘模型 | 四轮**差速/普通轮**，`V_y` 无效 | 支持 `MECANUM` 逆解，但 Nav2 用差速 | 保底都走差速 |
| 固件框架 | **ESP-IDF** | Arduino/PlatformIO | M2 选 ESP-IDF |
| 板载 IMU | **ICM42670P（有例程）** | 不支持该型号 | M2 用 Yahboom |
| ROS2 导航栈 | 无（资料包里的 `yahboomcar_*` 包不含在 GitHub） | **完整 Nav2 + SLAM + EKF** | M4 用 linorobot2 |
| 仿真 | 无 | **Gazebo 现成** | M4/M5 用 linorobot2 |
| 运输方式 | WiFi/UDP（例程）| serial 或 wifi | 需求要求串口 → 选 serial |
| 获取难度 | 源码在**虚拟机/资料包**，GitHub 只有 PDF | **GitHub 直接 clone** | — |
| 许可证 | 教程，源码未公开 | Apache-2.0 | 保留署名 |

**一句话总结**：**Yahboom 给"能开动的车"，linorobot2 给"会认路的车"。**两者不冲突，正好是 M2 与 M4 的分工。

## 7. 决策清单

| # | 决策 | 建议 | 影响 |
|---|---|---|---|
| D1 | 是否采用方案 C（混合） | **是** | M4 工作量大幅下降 |
| D2 | 是否引入 `/imu/data`（话题 5→6） | **是** | 定位更稳，代价是多 1 个话题 |
| D3 | `/odom` 是否改名为 `odom/unfiltered` | **不改，用 remap** | 避免动 M2 固件 |
| D4 | 是否启用 Gazebo 仿真 | **是** | M4/M5 无需硬件即可开发 |
| D5 | 是否启用麦轮横移 | **否（保底）** | Nav2 差速控制器本就不给横移 |
| D6 | M2 固件框架 | **ESP-IDF（Yahboom）** | 避开驱动/IMU 移植 |
| D7 | frame 命名 | 统一为 `odom` / `base_footprint` | 改 Yahboom 的 `odom_frame` |
