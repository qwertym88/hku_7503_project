# M2 手动测试步骤与命令

2026-11-19。适用于已烧录的反馈保护版正常 `/chassis` 固件，USB921600、domain42，轮距200×170mm、轮径65mm。操作者亲手执行；本页是测试步骤，不代表测试已通过。完整缺口见[M2进度清单](M2底盘进度与交付清单.md)。

先完成架空测试1～6，再安排地面/载荷验收。每一步观察正常再进入下一步；遇到某轮明显飞转、反转或故障位，停止该次测试并检查。电机运行时不换插头、不用手捏停轮子。

## 0. 终端、供电与日志

每个操作 ROS 的 zsh 终端先运行（bash 换成 setup.bash）：

```bash
cd /home/qwertym/Coding/hku_7503_project
source /opt/ros/jazzy/setup.zsh
export ROS_DOMAIN_ID=42
```

控制终端额外创建本轮记录目录；后文所有 `$M2_RUN_DIR` 命令在这个终端执行：

```bash
export M2_RUN_DIR="$PWD/tests/logs/m2_manual_$(date +%Y%m%d_%H%M%S)"
mkdir -p "$M2_RUN_DIR"
```

`tests/logs/` 被Git忽略，完成后将结果摘要和需归档的小文件放进 `tests/firmware/`，视频另存共享位置。工具不覆盖已有结果；重复测试更换文件名或创建新运行目录。

车轮全部架空、支架稳定；电机运动测试需接电池并打开主电源。USB通信正常不能证明电机电源已接好。唯一串口 agent：

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}'
```

已有运行中的 `hku-chassis-agent` 时直接使用。没有时才运行：

```bash
docker run -d --rm --name hku-chassis-agent \
  --network host --device /dev/ttyUSB0 \
  -e ROS_DOMAIN_ID=42 microros/micro-ros-agent:jazzy \
  serial --dev /dev/ttyUSB0 -b 921600 -v4
```

若重连没有节点，先停止所有速度发布者，再按板上RESET。**当前尚无上电零速解锁联锁，不要让非零速度发布者运行时按RESET。**

观察终端持续显示诊断：

```bash
ros2 topic echo /chassis/diagnostics std_msgs/msg/String \
  --qos-reliability best_effort --full-length
```

速度零值命令（只是软件停车，不能替代物理断电）：

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist '{}' \
  --rate 20 --times 5 --wait-matching-subscriptions 1 --max-wait-time-secs 5
```

需要停车时先结束当前非零速度发布者，再发零；严重异常直接切断电机主电源。

## 1. 通信与当前版本：只读

```bash
ros2 node list
ros2 topic info /cmd_vel -v
ros2 topic info /odom -v
ros2 topic echo /chassis/diagnostics std_msgs/msg/String \
  --qos-reliability best_effort --full-length --once --timeout 5
```

检查 `/chassis` 存在，未测试时 `/cmd_vel` 的 Publisher count=0、Subscription count=1，`/odom` 只有正常固件一个发布者。诊断应有 `feedback_missing_mask`、`feedback_reversed_mask`，否则不是本轮保护版。

静止预期：enabled=0、speed和pid_output全0；故障位均0；imu_state=1、imu_whoami=103、imu_valid=1、imu_errors不增长。`target` 停车后可能保留上一命令，不代表电机仍在输出。`battery_v` 只是ADC估算，电源是否足够要以负载/万用表验证。

## 2. 新M4编码器、四轮轮序与每转计数：手转

保持无速度发布者、enabled=0。在诊断窗口观察 `counts`，依次手转一个轮子；必要时关闭电机主电源、保留USB供电，先确认编码器仍有供电/计数。

| 俯视、车头朝上 | 数组项 | 电机 |
|---|---|---|
| 左前 | counts[0] | M1 |
| 左后 | counts[1] | M2 |
| 右前 | counts[2] | M3 |
| 右后 | counts[3] | M4（新电机） |

先测M4，转动时第四项必须变化，反转时计数变化方向相反；其他轮不动时对应计数应基本不变。再复核另外三轮。

给轮胎作记号，读转前计数C0，缓慢完整转一圈后读C1；当前假设 `abs(C1-C0)` 约1040。每轮正反各3次，减速箱间隙和对齐误差要记录；若稳定接近260/520/2080等不同值，停止里程计精度验收，先修正每转配置。诊断约2Hz，转完稍等再读。

用户已纠正轮ID接线：四轮朝车头滚动时原始 `counts` 增加，反向时减少。固件已参考 `4943022` 撤销四轮取反；`counts`增量与`speed`/`target`方向一致。方向恢复修订待烧录验证，旧“前进raw counts减小”说明不再适用。
手转后里程计会变化，这是架空/手转反馈，不是真实车体位移。下表分别列出反馈speed与原始计数增量，不看累计数本身正负。

## 3. IMU静态、频率、零偏：已完成本轮静态校准

2026-11-19已完成原始采集、零偏估计、板端启用及静态复测；本次IMU47.985Hz、odom20.001Hz，Z残余约0.03825°/s。证据见[校准完成记录](../../tests/firmware/2026-11-19_imu_calibration.md)。当前imu_bias_enabled=1，不要直接重复下面的原始校准；下一步先做第4节方向验证。以下仅供未来重新标定：先将imu_calibration.h开关改0并重新编译烧录。

停止全部速度发布者；按RESET，确认rx=0、enabled=0、imu_bias_enabled=0。让板卡正常运行预热约30～60秒、车体静止。然后采集35秒，采集期间不转轮子、不触碰车体：

```bash
/usr/bin/python3 tools/chassis_imu_probe.py \
  --duration 35 --warmup 5 --label stationary_raw \
  --output "$M2_RUN_DIR/imu_raw.json"

/usr/bin/python3 tools/chassis_imu_calibrate.py "$M2_RUN_DIR/imu_raw.json" \
  --confirm-stationary --header "$M2_RUN_DIR/imu_calibration_candidate.h"
```

预期IMU接收约50Hz、odom约20Hz，无明显丢段/倒退；同一主机当前正常时间戳年龄可参考此前5～12ms，只是参考值，不是已冻结的验收上限。加速度模长约9.81m/s²，平放Z约+9.8；X/Y小偏量不直接当作加速度偏置。

重新标定时采集的是尚未补偿的陀螺，静止不为0是待校准现象，重点记录三轴均值、标准差和前后半段稳定性。校准拒绝时先看提示：是否rx非0、已有补偿、碰动车体、轮子转动、数据不足或时间戳异常；不放宽门限强行生成。

候选文件生成不改变板端固件。记录结果后再安排复制到 `firmware/chassis/main/imu_calibration.h`、build/flash并静置复测；不要直接用已补偿数据再次估计原始零偏。

## 4. IMU轴方向与陀螺符号：手动姿态动作

确认无速度发布者、电机停止。分别观察：

```bash
ros2 topic echo /imu/data sensor_msgs/msg/Imu \
  --qos-reliability best_effort --field linear_acceleration
```

| 动作（每次从平放开始，静止保持后读加速度） | 相对平放时的预期变化 |
|---|---|
| 车头抬高约10～20° | acceleration.x正向增加 |
| 车左侧抬高约10～20° | acceleration.y正向增加 |
| 回到平放 | acceleration.z约+9.8m/s² |

退出上一个echo后看陀螺：

```bash
ros2 topic echo /imu/data sensor_msgs/msg/Imu \
  --qos-reliability best_effort --field angular_velocity
```

| 动作（看动作进行中的读数） | 预期符号，须明显超过静态零偏 |
|---|---|
| 从上方看，车头逆时针转 | angular_velocity.z正 |
| 从上方看，顺时针转 | angular_velocity.z负 |
| 正在抬高左侧 | angular_velocity.x正 |
| 正在抬高车头 | angular_velocity.y负 |

陀螺停止转动后回到静态偏置附近；抬高后保持静止时，不应仍有大的旋转角速度。原始IMU无姿态解算，orientation的w=1不是“车体始终水平”的测量结果。

如需保存动作，先在控制终端启动20秒只读采集，再按固定时间段做一个动作（例如2～7秒缓慢抬高、7～12秒保持、12～17秒放回），记录实际动作窗口：

```bash
/usr/bin/python3 tools/chassis_imu_probe.py --duration 20 --warmup 0 \
  --label nose_up --output "$M2_RUN_DIR/imu_nose_up.json"
```

其他动作单独采集并换label/文件名；动作数据不用于零偏标定。

## 5. 四轮闭环：每次1秒，一个一个执行

重新确认电机电池/主电源已打开，诊断无锁存故障。保持观察窗口。先执行前进，观察正常才执行后面的命令；不要整段一次粘贴执行。

```bash
/usr/bin/python3 tools/chassis_bench_test.py forward --confirm-wheels-raised \
  --duration 1 --output "$M2_RUN_DIR/forward.json"
```

```bash
/usr/bin/python3 tools/chassis_bench_test.py reverse --confirm-wheels-raised \
  --duration 1 --output "$M2_RUN_DIR/reverse.json"
```

```bash
/usr/bin/python3 tools/chassis_bench_test.py left --confirm-wheels-raised \
  --duration 1 --output "$M2_RUN_DIR/left.json"
```

```bash
/usr/bin/python3 tools/chassis_bench_test.py right --confirm-wheels-raised \
  --duration 1 --output "$M2_RUN_DIR/right.json"
```

下表“前/后”指该轮能驱动车辆朝前/后的转动方向，不是从左右两侧看电机轴都同为顺时针。车轮表面朝车前的最高点，在前进滚动时相对车体向车前运动。

| 动作 | M1/M2左侧 | M3/M4右侧 | 反馈speed符号 | 原始counts增量符号 | odom.twist.twist |
|---|---|---|---|---|---|
| forward，vx=+0.03 | 前进 | 前进 | + + + + | + + + + | linear.x正，angular.z接近0 |
| reverse，vx=-0.03 | 后退 | 后退 | - - - - | - - - - | linear.x负，angular.z接近0 |
| left，wz=+0.15 | 后退 | 前进 | - - + + | - - + + | angular.z正，linear.x接近0 |
| right，wz=-0.15 | 前进 | 后退 | + + - - | + + - - | angular.z负，linear.x接近0 |

前后直行目标约±1.53 count/10ms，约153 count/秒；转向每轮目标绝对值约1.41 count/10ms。这是目标参考，不把1秒实际增量要求精确等于153；先确认方向、持续计数、速度是否大致一致与M4是否不再异常飞转。

额外终端可观察：

```bash
ros2 topic echo /odom nav_msgs/msg/Odometry --field twist.twist
```

通过基本条件：四轮物理方向正确、四路反馈方向正确且持续变化，无一轮明显高速失控/完全不动；结束后四轮实际停止、enabled=0、pid_output全0，两种故障mask为0。每种动作至少重复3次（改文件名），记录稳定性。`pulse_completed`只是软件结果，不能替代人眼观察。

故障解读：missing表示无反馈/疑似堵转/失电，reversed表示净反馈方向相反。mask 1/2/4/8分别M1/M2/M3/M4，组合值按位解释。例如8对应M4；12对应M3+M4。

故障锁存后，先结束所有速度发布者、检查接线/供电；需要换线时先断开电池与USB。修复后再上电/RESET并确认mask=0；不要反复重启掩盖故障。

## 6. 看门狗与通信中断停车

先通过第5步。普通台架脚本结束会主动发零速，只能验证主动停车；下列测试专门验证没有新命令时的停车。诊断2Hz不足以精确证明≤0.5秒，需要实际车轮视频与命令/通信停止时刻对照，逐次记录。

### 6A. 有限发送结束后自动停车

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.03}, angular: {z: 0.0}}' \
  --rate 20 --times 40 --keep-alive 0 \
  --wait-matching-subscriptions 1 --max-wait-time-secs 5
```

约2秒命令后发布者退出，没有额外零速消息；从最后一条有效指令到四轮实际停转应≤0.5秒。观察enabled最终0、speed最终0、故障mask保持0；target可能仍保留上一目标。至少测3次。不要用最后打印退出时刻替代准确的最后消息时刻而高估精度。

### 6B. 发布进程被终止

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.03}, angular: {z: 0.0}}' \
  --rate 20 --wait-matching-subscriptions 1 --max-wait-time-secs 5
```

轮子稳定转动后按Ctrl+C，观察同样≤0.5秒停车。若要测强杀进程，应明确识别本次发布者PID，不能模糊pkill所有ROS/Python进程；本页不提供广泛杀进程命令。

### 6C. agent退出

再次运行上面的连续速度发布命令，在另一终端执行：

```bash
docker stop --time 0 hku-chassis-agent
```

观察物理停车；此时诊断通信也会中断，没有新诊断是预期现象。**先Ctrl+C结束宿主机速度发布者**，再重建agent（第0步Docker命令）并按RESET。恢复后无速度发布者时四轮不得自行转动。当前固件通信异常后需RESET，未实现自动恢复。

### 6D. USB数据线拔除

确认电池能独立给控制板/电机供电。连续发布低速命令，转动稳定后拔电脑到控制板的USB数据线，观察≤0.5秒停车及板卡是否仍有电。若板卡也掉电，只证明掉电停机，不能证明独立看门狗。

先Ctrl+C结束宿主机速度发布者，再接回USB，确认设备名；停止旧agent并按第0步重建agent，必要时RESET。Docker旧容器可能仍绑定拔线前的设备，不能只换个容器名并行启动。恢复通信后静止检查无自动续跑。

## 7. 反馈故障锁存：可选台架故障注入

先完成正常四轮与停车测试。不要用手堵轮，不热插拔编码器/电机线。若需要实测无反馈锁存，可先关闭电机电源并断开电池、USB，拔下M4整根电机线束，保持其他通道连接；重新供电并架空。该步骤模拟的是M4整路无反馈，不能单独区分编码器故障与电机断电。

此时单独执行一次第5步forward命令、换新的输出名。其他轮可能短暂转动，随后应全部停下，feedback_missing_mask包含8、enabled=0，后续非零命令不能解除锁存。若需要验证锁存，保持故障不修复，仅发送有限10条非零速度：

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.03}, angular: {z: 0.0}}' \
  --rate 20 --times 10 --keep-alive 0 \
  --wait-matching-subscriptions 1 --max-wait-time-secs 5
```

预期仍全部不转，rx/rejected增长、故障位保持。300ms是检测窗口，不等于已测出的物理停车时延；不因2Hz诊断刷新晚就直接判定检测超时。

停止所有发布者后彻底断电，恢复M4线束，再供电/RESET，mask应归零并重新做forward基本检查。反向反馈不通过故意改接AB线来测；其软件注入回归已有，若实际发生按接线/符号故障处理。
