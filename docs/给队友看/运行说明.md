# 固定路线方案运行与交接

更新2026-11-19。环境：Ubuntu24.04、ROS2 Jazzy、Pi5经USB串口连接ESP32。当前已有QR、旧导航包及已烧录的底盘 odom/IMU 接口；**建图/定位的新接线与模式启动、固定路线执行器、mission与统一bringup尚待实现**。架构见[建图定位与固定路线方案](建图定位与固定路线方案.md)。本页区分已有操作与负责人需补充的命令，不提供虚构的一键启动。

## 已有工作区构建

从仓库根目录，使用bash终端：

```bash
source /opt/ros/jazzy/setup.bash
cd ros2_ws
colcon build --symlink-install
source install/setup.bash
export ROS_DOMAIN_ID=42
```

预期已有包构建成功；不表示mission已存在。每个新终端先source /opt/ros/jazzy/setup.bash与工作区install/setup.bash；zsh使用对应setup.zsh。跨机调试不设置LOCALHOST发现限制。

## 固定路线启动顺序（待实现清单）

1. M1/M3按冻结起点复摆，确认货架、放置位、地面与路线版本一致；M2确认供电/急停、举升处于已确认低位。
2. M2启动micro-ROS agent和固件，检查原始/odom、/imu/data及时间戳，并确认固件不重复发布EKF负责的局部TF。本机已验证串口 `/dev/ttyUSB0`、921600、domain42；使用下方 Docker 命令，或已安装时运行 `ros2 run micro_ros_agent micro_ros_agent serial --dev /dev/ttyUSB0 -b 921600`。Pi 固定设备名和桥接包启动脚本仍待实现。
3. M4/M5先用建图模式启动真雷达、改造后的EKF与slam_toolbox，实际移动采图并存图；结束建图后切执行模式：真雷达、同一EKF、map_server+AMCL和固定路线mission。初始化地图中的真实出生位姿，确认局部与全局TF可用。不启动Nav2 planner/controller或旧waypoint_driver，执行时不运行SLAM。
4. 检查/cmd_vel仅有当前执行器一个发布者；未人工开始时必须零速。M5新增的开始/取消入口、配置路径与完整命令在实现后填下表。
5. 人工启动一次，自动执行冻结顺序；结束/故障即零速、保持支撑；重新执行必须人工复位与复摆。

## 已验证的本机底盘操作

从仓库根目录构建：`bash firmware/chassis/idf.sh build`；烧录步骤见[固件说明](../../firmware/chassis/README.md)。当前正常应用已包含 IMU，不需为了观察接口重复烧录。新 M4 已更换待复测，先确认架空及反馈；整车运动与精度验收未通过。

同一串口只保留一个 agent，在本机已有 Docker 镜像时运行：

```bash
docker run --rm --name hku-chassis-agent --network host --device /dev/ttyUSB0 \
  -e ROS_DOMAIN_ID=42 microros/micro-ros-agent:jazzy \
  serial --dev /dev/ttyUSB0 -b 921600 -v4
```

已有容器则用 `docker logs -f --tail 30 hku-chassis-agent` 查看，`docker stop hku-chassis-agent` 停止；退出日志不停止后台容器。`--rm` 容器停止后需重建。复连异常先排除串口占用，再重建 agent 并按板上 RESET；固件没有自动断线恢复。完整状态、IMU 零偏/时间戳限制及验收顺序见[M2清单](M2底盘进度与交付清单.md)。

## 已有接口观察

先完成上面的环境source和agent启动：

```bash
ros2 topic echo /odom --once
ros2 topic echo /imu/data --qos-reliability best_effort --once
ros2 topic echo /odometry/filtered --once
ros2 run tf2_ros tf2_echo map base_footprint
ros2 topic hz /odom
ros2 topic info /cmd_vel -v
```

应有新鲜反馈、正确frame和唯一速度发布者。原始/odom输入EKF，EKF输出/odometry/filtered和局部TF；固定路段使用滤波局部反馈。不上relay，不将EKF输出映射回/odom。tf2_echo须定位模式就绪后运行。

## 记录证据

自动运行前另开终端，先source环境，再录制（ROS2 bag为标准命令，需本机具备rosbag2）：

```bash
ros2 bag record -o /tmp/fixed_route_run /odom /odometry/filtered /imu/data /scan /amcl_pose /tf /tf_static /cmd_vel /lifter
```

执行模式中/scan、滤波局部反馈与地图定位均必需；建图时AMCL不运行，另存建图bag。正式地图.yaml/.pgm独立保存；录包时核实静态TF已被捕获。/tmp/fixed_route_run每次换唯一名称，运行后及时复制到共享存储；bag不自动代替状态机日志与外部测量。所有结果按[验收协议](../../tests/保守方案验收.md)归档。

## M2升降（180°位置舵机）

位置控制新版已在本次IMU记录中确认运行；端点/载荷运动尚未验收。在底盘停稳且通信正常时，直接发送：

```bash
# 上升至menuconfig配置的最高角度，默认80°；等待结束后持续保持
ros2 topic pub /lifter std_msgs/msg/UInt8 '{data: 1}' --once
# 等实际停稳后下降至最低角度，默认0°
ros2 topic pub /lifter std_msgs/msg/UInt8 '{data: 0}' --once
```

上述80°为代码缺省；本次实际运行配置是下0°/上75°，稳定等待各1200ms。无需arm，旧arm/jog服务已移除。`Chassis lifter (180-degree position servo)`菜单的LOWER_DEG/UPPER_DEG设置角度，UP_MS/DOWN_MS仅为稳定等待。首次命令前无PWM位置输出，stop撤销PWM、不能保证中间位置保持。端点标定、停止/恢复与烧录见[升降说明](../../firmware/chassis/LIFTER.md)。
